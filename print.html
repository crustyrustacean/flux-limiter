Flux Limiter Documentation

Flux Limiter

A simple rate limiter based on the Generic Cell Rate Algorithm (GCRA) with nanosecond precision and lock-free per-client updates.

Features

  • Precise: Implements the GCRA algorithm in integer nanoseconds. The rate is rounded to a whole-nanosecond interval, which is exact for any rate that divides one billion
  • Generic client IDs: Works with any hashable client identifier (String, IpAddr, u64, etc.)
  • Rich metadata: Returns detailed decision information for HTTP response construction
  • Unaffected by clock changes: The default clock measures elapsed time, so an operating-system clock correction cannot lock clients out
  • Memory efficient: One atomic timestamp per client. Idle clients are removed when you call cleanup_stale_clients(); nothing runs in the background
  • Robust error handling: Invalid configuration is rejected with an error, and the default clock cannot fail
  • Testable: Clock abstraction enables deterministic testing
  • Thread-safe: Safe to use across multiple threads

What is Rate Limiting?

Rate limiting is a technique used to control the rate at which requests or operations are processed. It’s commonly used to:

  • Protect services: Prevent abuse and ensure fair resource allocation
  • Control costs: Limit API usage to manage infrastructure costs
  • Ensure quality of service: Prevent individual users from degrading performance for others
  • Comply with policies: Enforce usage limits and SLA agreements

Why Flux Limiter?

Flux Limiter stands out with its focus on:

  1. Correctness: GCRA in integer arithmetic, with no floating-point state
  2. Performance: O(1) operations, and updating a known client takes no lock
  3. Reliability: Invalid configuration is reported, and rate limiting does not depend on the operating-system clock being correct
  4. Observability: Rich metadata for monitoring and HTTP headers
  5. Flexibility: Generic design supporting various client ID types

Alternatives

Flux Limiter is one of several rate limiters on crates.io. These are the others we know of, described by what they do. Each claim below was checked against the published version at the time of writing.

  • governor: GCRA with one 64-bit value of state per limiter, updated by compare-and-swap.
    • keyed limiters for many clients, and checks that cost more than one cell
    • can wait asynchronously until a request is allowed (until_ready, until_key_ready)
    • denial reports how long to wait, as a relative Duration
    • pluggable clock, with five shipped, including one you control in tests
    • optional no_std
  • leaky-bucket: a token bucket for async code.
    • tokens, a refill interval, and how many tokens are refilled per interval
    • acquire(n).await suspends the caller until n tokens are available
    • try_acquire(n) answers with a bool: no wait time, no remaining count
    • one limiter is one bucket; there is no per-client key
    • requires a Tokio runtime
  • quota: a pool of per-key GCRA states, like Flux Limiter.
    • keys are passed by reference, and a check can cost more than one token
    • the result reports how much quota remains, but says nothing about time: no wait duration and no reset time
    • built on quanta for its clock

Where Flux Limiter differs:

  • Every check returns the seconds to wait and the time the limit resets, as a Unix-epoch timestamp. None of the three report a reset time.
  • It has no runtime requirement and links 11 crates in total. leaky-bucket requires Tokio.
  • The key can be passed by reference (check_request_ref), as with governor and quota, so a String key is not cloned per request.

What it does not have:

  • Weighted checks, async waiting, or no_std. governor has all three.

Algorithm: GCRA

Flux Limiter implements the Generic Cell Rate Algorithm (GCRA), which is mathematically equivalent to the token bucket algorithm but offers several advantages:

  • No background token refill processes
  • No floating-point state: once the rate is a whole-nanosecond interval, the arithmetic is exact
  • Efficient state representation (one timestamp per client)
  • Deterministic behavior with integer arithmetic

Performance Characteristics

  • Memory: O(number of active clients)
  • Time complexity: O(1) for check_request() operations
  • Concurrency: Each client’s state is a single atomic in a sharded DashMap; updating a known client is a compare-and-swap with no lock
  • Precision: Nanosecond resolution. The rate interval is rounded to a whole number of nanoseconds
  • Reliability: The default clock is monotonic, so a backwards clock step does not deny requests

Add Flux Limiter to your Rust project using Cargo.

Quick Start

Get started with Flux Limiter in just a few minutes.

Basic Example

#![allow(unused)]
fn main() {
use flux_limiter::{FluxLimiter, FluxLimiterConfig, MonotonicClock};

// Create a rate limiter: 10 requests per second with burst of 5
let config = FluxLimiterConfig::new(10.0, 5.0);
let limiter = FluxLimiter::with_config(config, MonotonicClock::new()).unwrap();

// Check if a request should be allowed
match limiter.check_request("user_123") {
    Ok(decision) => {
        if decision.allowed {
            println!("Request allowed");
        } else {
            println!("Rate limited - retry after {:.2}s",
                     decision.retry_after_seconds.unwrap_or(0.0));
        }
    }
    Err(e) => {
        eprintln!("Rate limiter error: {}", e);
        // Handle error appropriately (e.g., allow request, log error)
    }
}
}

Understanding the Example

Let’s break down what’s happening:

  1. Create Configuration: FluxLimiterConfig::new(10.0, 5.0)

    • Rate: 10 requests per second
    • Burst: 5 additional requests allowed in bursts
    • Total capacity: ~6 requests can be made immediately

  2. Create Rate Limiter: FluxLimiter::with_config(config, MonotonicClock::new())

    • Uses the configuration
    • Uses MonotonicClock, the default monotonic time source, which is unaffected by OS clock steps
    • Returns Result to handle configuration errors

  3. Check Request: limiter.check_request("user_123")

    • Checks if the client “user_123” can make a request
    • Returns rich metadata about the decision
    • Automatically updates internal state

Decision Metadata

The FluxLimiterDecision struct provides detailed information:

#![allow(unused)]
fn main() {
#[non_exhaustive]
pub struct FluxLimiterDecision {
    pub allowed: bool,                    // Whether to allow the request
    pub retry_after_seconds: Option<f64>, // When to retry (if denied)
    pub remaining_capacity: Option<f64>,  // Remaining burst capacity
    pub reset_time_nanos: u64,           // When the window resets
}
}

The #[non_exhaustive] attribute means fields may be added in future versions without a breaking change. You can still access all fields via dot notation.

Using Decision Metadata

#![allow(unused)]
fn main() {
match limiter.check_request("user_123") {
    Ok(decision) => {
        if decision.allowed {
            println!("Request allowed");
            if let Some(remaining) = decision.remaining_capacity {
                println!("Remaining capacity: {:.2}", remaining);
            }
        } else {
            if let Some(retry_after) = decision.retry_after_seconds {
                println!("Please retry after {:.2} seconds", retry_after);
            }
        }
    }
    Err(e) => {
        eprintln!("Error: {}", e);
    }
}
}

Thread Safety

Flux Limiter is thread-safe and can be shared across threads:

#![allow(unused)]
fn main() {
use std::sync::Arc;
use std::thread;

let config = FluxLimiterConfig::new(10.0, 5.0);
let limiter = Arc::new(FluxLimiter::with_config(config, MonotonicClock::new()).unwrap());

let mut handles = vec![];

for i in 0..10 {
    let limiter = Arc::clone(&limiter);
    let handle = thread::spawn(move || {
        let client_id = format!("user_{}", i);
        limiter.check_request(client_id)
    });
    handles.push(handle);
}

for handle in handles {
    let result = handle.join().unwrap();
    println!("Result: {:?}", result);
}
}

Configuration

Learn how to configure Flux Limiter for your specific use case.

Configuration Basics

Flux Limiter uses FluxLimiterConfig for configuration:

#![allow(unused)]
fn main() {
use flux_limiter::FluxLimiterConfig;

let config = FluxLimiterConfig::new(rate_per_second, burst_capacity);
}

Rate Parameter

The rate parameter defines the sustained requests per second.

  • Must be finite: NaN and ±Infinity are rejected
  • Must be positive (> 0)
  • Must be at most 1_000_000_000 (1 billion requests per second): the rate interval is stored as whole nanoseconds, so a higher rate has no representable interval
  • Defines the steady-state request rate
  • Example: rate = 100.0 means 100 requests per second
#![allow(unused)]
fn main() {
// 100 requests per second sustained
let config = FluxLimiterConfig::new(100.0, 0.0);
}

Understanding Rate

The rate translates to a time interval between requests:

  • rate = 1.0 → One request per second (1000ms interval)
  • rate = 10.0 → Ten requests per second (100ms interval)
  • rate = 100.0 → One hundred requests per second (10ms interval)

Burst Parameter

The burst parameter defines additional capacity for handling bursts.

  • Must be finite: NaN and ±Infinity are rejected
  • Must be non-negative (≥ 0)
  • Must be small enough to fit: burst × (1_000_000_000 / rate) is stored as a 64-bit nanosecond count, so a burst whose tolerance would exceed 2^64 nanoseconds (about 584 years) is rejected
  • Allows temporary spikes above the sustained rate
  • Example: burst = 50.0 allows bursts of ~50 additional requests
#![allow(unused)]
fn main() {
// 100 requests per second with burst capacity of 50
let config = FluxLimiterConfig::new(100.0, 50.0);
}

Understanding Burst

  • Total capacity: Approximately 1 + burst requests can be made immediately
  • Burst recovery: Unused burst capacity accumulates at the configured rate
  • Maximum burst: Capped at the configured burst value

Rate and Burst Example

With rate=10.0 and burst=5.0:

  1. Initial state: Client can make ~6 requests immediately (1 + 5 burst)
  2. After burst: Limited to sustained rate of 10 requests per second
  3. Recovery: Burst capacity recovers at 10 units per second
  4. After 1 second idle: Can make ~6 requests again

Builder Pattern

Use the builder pattern for clearer configuration:

#![allow(unused)]
fn main() {
let config = FluxLimiterConfig::new(0.0, 0.0)
    .rate(100.0)        // 100 requests per second
    .burst(50.0);       // Allow bursts of up to 50 requests
}

This approach is especially useful when you want to:

  • Start with default values and override specific settings
  • Make configuration changes clearer and more readable

Configuration Validation

Configuration is validated when creating the rate limiter:

#![allow(unused)]
fn main() {
use flux_limiter::{FluxLimiterConfig, FluxLimiterError};

// Invalid configuration: negative rate
let config = FluxLimiterConfig::new(-10.0, 5.0);
match FluxLimiter::with_config(config, MonotonicClock::new()) {
    Ok(_) => println!("Valid configuration"),
    Err(FluxLimiterError::InvalidRate) => {
        eprintln!("Error: Rate must be positive");
    }
    Err(e) => eprintln!("Error: {}", e),
}
}

Validation Rules

  • InvalidRate: Returned if rate is not finite, is ≤ 0, or is > 1,000,000,000
  • InvalidBurst: Returned if burst is not finite, is < 0, or is too large for the configured rate

Rate is checked first: a configuration with both an invalid rate and an invalid burst reports InvalidRate.

Every rejected configuration is rejected at construction time as well, so FluxLimiter::with_config never returns a limiter built from invalid values.

Precision: whole-nanosecond truncation

The rate interval (1_000_000_000 / rate) and the burst tolerance (burst × interval) are stored as whole nanoseconds. Values that are not a whole number of nanoseconds are truncated, not rounded. This is deliberate: integer arithmetic keeps every timing decision exact and reproducible.

In practice this is invisible at ordinary rates, but it has two visible consequences:

  • A fractional burst can truncate to nothing, but only at very high rates. The tolerance is burst × interval in nanoseconds, so it is lost entirely when that product is under 1 ns. At rate = 10.0 the interval is 100 ms and even burst = 0.004 keeps a 0.4 ms tolerance. But at rate = 1e8 the interval is 10 ns, so burst = 0.05 asks for 0.5 ns and gets no burst at all, while burst = 0.1 (exactly 1 ns) is preserved.
  • A rate that does not divide one billion is enforced higher than requested. The interval is exact only when 1_000_000_000 / rate is a whole number. Below about 10 million per second the discarded fraction is under 1% and not noticeable. Above that it grows quickly, because the interval is only a few nanoseconds and a fraction of one is a large share of it. For example rate = 6e8 has a true interval of 1.667 ns, which truncates to 1 ns, so the limiter enforces 1e9 requests per second: 67% more than asked for.
Requested rateInterval (ns)Enforced rateDifference
1e8101.0e80%
1.5e861.6667e8+11.1%
2.5e842.5e80%
4e825.0e8+25.0%
6e811.0e9+66.7%

If you need an exact limit, choose a rate that divides 1,000,000,000 evenly (such as 1e8, 1e6, 1000.0, 10.0, 1.0); those are enforced exactly.

Dynamic Configuration

While Flux Limiter doesn’t support runtime configuration changes, you can work around this:

#![allow(unused)]
fn main() {
use std::sync::Arc;
use parking_lot::RwLock;

struct DynamicRateLimiter {
    limiter: Arc<RwLock<FluxLimiter<String, MonotonicClock>>>,
}

impl DynamicRateLimiter {
    fn update_config(&self, new_config: FluxLimiterConfig) {
        let new_limiter = FluxLimiter::with_config(new_config, MonotonicClock::new()).unwrap();
        *self.limiter.write() = new_limiter;
    }

    fn check_request(&self, client_id: String) -> Result<FluxLimiterDecision, FluxLimiterError> {
        self.limiter.read().check_request(client_id)
    }
}
}

Note: Changing configuration resets all client state.

Basic Usage

Common patterns and best practices for using Flux Limiter.

Simple Rate Limiting

The most basic use case - check if a request should be allowed:

#![allow(unused)]
fn main() {
use flux_limiter::{FluxLimiter, FluxLimiterConfig, MonotonicClock};

let config = FluxLimiterConfig::new(10.0, 5.0);
let limiter = FluxLimiter::with_config(config, MonotonicClock::new()).unwrap();

match limiter.check_request("user_123") {
    Ok(decision) if decision.allowed => {
        // Process request
        println!("Request allowed");
    }
    Ok(decision) => {
        // Rate limited
        println!("Rate limited - retry after {:.2}s",
                 decision.retry_after_seconds.unwrap_or(0.0));
    }
    Err(e) => {
        // Handle error
        eprintln!("Error: {}", e);
    }
}
}

Working with Different Client ID Types

String Client IDs

For String keys, use check_request_ref and pass a &str. It does not copy the key for a client the limiter already knows, so a request costs no allocation:

#![allow(unused)]
fn main() {
// User IDs, session IDs, API keys
let limiter = FluxLimiter::<String, _>::with_config(config, MonotonicClock::new()).unwrap();

limiter.check_request_ref("user_123")?;
limiter.check_request_ref("session_abc")?;
}

check_request takes the key by value, so with it a caller who holds a &str has to build a String for every request. The two methods make the same decisions; only the way the key is passed differs. If you already own the key, check_request moves it without copying:

#![allow(unused)]
fn main() {
let owned: String = get_client_id();
limiter.check_request(owned)?;
}

IP Address Client IDs

#![allow(unused)]
fn main() {
use std::net::IpAddr;

let limiter = FluxLimiter::<IpAddr, _>::with_config(config, MonotonicClock::new()).unwrap();

let client_ip: IpAddr = "192.168.1.1".parse().unwrap();
limiter.check_request(client_ip)?;
}

Numeric Client IDs

#![allow(unused)]
fn main() {
// Numeric IDs avoid string allocation overhead
let limiter = FluxLimiter::<u64, _>::with_config(config, MonotonicClock::new()).unwrap();

fn main() {
use std::time::{SystemTime, UNIX_EPOCH, Duration};

match limiter.check_request("user_123") {
    Ok(decision) => {

Sharing Across Threads

Flux Limiter is thread-safe and designed to be shared:

Using Arc

#![allow(unused)]
fn main() {
use std::sync::Arc;
use std::thread;

let config = FluxLimiterConfig::new(100.0, 50.0);
let limiter = Arc::new(FluxLimiter::with_config(config, MonotonicClock::new()).unwrap());

// Share across multiple threads
let handles: Vec<_> = (0..10)
    .map(|i| {
        let limiter = Arc::clone(&limiter);
        thread::spawn(move || {
            let client_id = format!("client_{}", i);
            limiter.check_request(client_id)
        })
    })
    .collect();

for handle in handles {
    match handle.join().unwrap() {
        Ok(decision) => println!("Allowed: {}", decision.allowed),
        Err(e) => eprintln!("Error: {}", e),
    }
}
}

Using Clone

FluxLimiter implements Clone — cloning shares the same DashMap client state, providing the same shared-state semantics without an outer Arc:

#![allow(unused)]
fn main() {
let config = FluxLimiterConfig::new(100.0, 50.0);
let limiter = FluxLimiter::with_config(config, MonotonicClock::new()).unwrap();

// Clone directly — both share the same client state
let limiter1 = limiter.clone();
let limiter2 = limiter.clone();

let handles: Vec<_> = (0..10)
    .map(|i| {
        // Clone for each thread
        let limiter = limiter.clone();
        thread::spawn(move || {
            let client_id = format!("client_{}", i);
            limiter.check_request(client_id)
        })
    })
    .collect();
}

Async Usage

While Flux Limiter is synchronous, it works seamlessly in async contexts:

use std::sync::Arc;
use tokio;

#[tokio::main]
async fn main() {

    // Use in async tasks
    let limiter_clone = Arc::clone(&limiter);

    .unwrap();
}

Multiple Rate Limiters

You can create different rate limiters for different purposes:

#![allow(unused)]
fn main() {
// Global rate limiter
let global_limiter = FluxLimiter::with_config(
    FluxLimiterConfig::new(1000.0, 500.0),
    MonotonicClock::new()
).unwrap();

// Per-user rate limiter
let user_limiter = FluxLimiter::with_config(
    FluxLimiterConfig::new(10.0, 5.0),
    MonotonicClock::new()
).unwrap();

// Apply both limits
fn check_both_limits(user_id: &str) -> bool {
    match global_limiter.check_request("global") {
        Ok(decision) if !decision.allowed => return false,
        Err(_) => return false,
        _ => {}
    }

    match user_limiter.check_request(user_id) {
        Ok(decision) => decision.allowed,
        Err(_) => false,
    }
}
}

Idiomatic Error Handling

#![allow(unused)]
fn main() {
use flux_limiter::{FluxLimiter, FluxLimiterError};

fn process_request(limiter: &FluxLimiter<String, MonotonicClock>, client_id: String) -> Result<(), String> {
    let decision = limiter
        .check_request(client_id)
        .map_err(|e| format!("Rate limiter error: {}", e))?;

    if !decision.allowed {
        return Err(format!(
            "Rate limited. Retry after {:.2}s",
            decision.retry_after_seconds.unwrap_or(0.0)
        ));
    }

    // Process the request
    Ok(())
}
}

Error Handling

Comprehensive guide to handling errors in Flux Limiter.

Error Types

Flux Limiter provides a well-defined error hierarchy:

#![allow(unused)]
fn main() {
pub enum FluxLimiterError {
    InvalidRate,           // Configuration: rate non-finite, ≤ 0, or > 1e9
    InvalidBurst,          // Configuration: burst non-finite, < 0, or too large to fit
    ClockError(ClockError), // Runtime: clock failure
}

pub enum ClockError {
    SystemTimeError,       // System time unavailable
}
}

Configuration Errors

Configuration errors occur when creating a rate limiter with invalid settings.

InvalidRate Error

Returned when the rate is not a finite number (NaN or ±Infinity), is ≤ 0, or is greater than 1,000,000,000 requests per second.

#![allow(unused)]
fn main() {

InvalidBurst Error

Returned when the burst is not a finite number, is negative, or is too large for the configured rate. The burst tolerance is burst × (1e9 / rate) nanoseconds and must fit in 64 bits (about 584 years), so a very large burst combined with a slow rate is rejected.

Runtime Clock Errors

Clock errors can occur during normal operation when the system clock is unavailable or behaves unexpectedly.

Understanding Clock Errors

With the default MonotonicClock, clock errors do not happen: it never returns one.

They can happen only if you pass SystemClock explicitly or write your own clock. With SystemClock there is one cause: the system clock is before the Unix epoch, so it cannot be read as a time since the epoch.

Not a clock error: A clock that steps backwards is not a source of ClockError. Reading the clock still succeeds and simply returns an earlier value. With SystemClock that makes clients look over-limit until the clock catches back up, with no error reported. This is why SystemClock is not the default.

Error Handling Policies

Different applications require different error handling strategies.

Fail-Open Policy

Allow requests when the rate limiter encounters errors:

#![allow(unused)]
fn main() {
fn should_allow_request(
    limiter: &FluxLimiter<String, MonotonicClock>,
    client_id: &str
) -> bool {
    match limiter.check_request_ref(client_id) {
        Ok(decision) => decision.allowed,
        Err(FluxLimiterError::ClockError(_)) => {
            // Fail-open: allow request on clock error
            eprintln!("Clock error - allowing request (fail-open policy)");
            true
        }
        Err(e) => {
            eprintln!("Rate limiter error: {} - allowing request", e);
            true
        }
    }
}
}

Use when:

  • Availability is more important than strict rate limiting
  • False positives (allowing too many requests) are acceptable
  • Your backend can handle temporary spikes

Deny requests when the rate limiter encounters errors:

Circuit Breaker Pattern

Temporarily bypass rate limiting after consecutive failures:

#![allow(unused)]
fn main() {
use std::sync::atomic::{AtomicU64, Ordering};

struct CircuitBreakerLimiter {
    limiter: FluxLimiter<String, MonotonicClock>,
    consecutive_failures: AtomicU64,
    failure_threshold: u64,
    bypassed: AtomicU64,
}

impl CircuitBreakerLimiter {
    fn check_request(&self, client_id: String) -> bool {
        // Check if circuit is open
        if self.consecutive_failures.load(Ordering::Relaxed) >= self.failure_threshold {
            self.bypassed.fetch_add(1, Ordering::Relaxed);
            eprintln!("Circuit open - bypassing rate limiter");
            return true;
        }

        match self.limiter.check_request(client_id) {
            Ok(decision) => {
                // Reset failure counter on success
                self.consecutive_failures.store(0, Ordering::Relaxed);
                decision.allowed
            }
            Err(FluxLimiterError::ClockError(_)) => {
                let failures = self.consecutive_failures.fetch_add(1, Ordering::Relaxed) + 1;

                if failures >= self.failure_threshold {
                    eprintln!("Opening circuit after {} consecutive failures", failures);
                }

                true // Fail-open
            }
            Err(e) => {
                eprintln!("Unexpected error: {}", e);
                false
            }
        }
    }
}
}

Advanced Usage

Advanced features and optimization techniques for Flux Limiter.

Memory Management

Flux Limiter tracks state for each client, which can grow over time. Use cleanup to manage memory.

Understanding Memory Usage

  • Memory: O(number of active clients)
  • Per-client overhead: about 31 bytes with a u64 key and about 76-95 bytes with a short String key, measured as the average over a million or more clients
  • It grows in steps, not smoothly: the client map doubles its tables when it fills, so memory holds flat for a while and then jumps. At any one client count the true figure is between about two thirds and the whole of the average above
  • Example: 1 million clients take about 34 MB with u64 keys

Performance Optimization

Minimize String Allocations

For a String-keyed limiter, pass the key as a &str with check_request_ref. It hashes and compares the borrowed key directly, and copies it only on the request that first adds the client. A request for a client the limiter already knows makes no allocation:

#![allow(unused)]
fn main() {
fn check_request_borrowed(limiter: &FluxLimiter<String, MonotonicClock>, id: &str) -> bool {
    limiter.check_request_ref(id).unwrap().allowed
}
}

check_request takes the key by value. Use it when you already own a String, and it moves the key instead of copying it:

#![allow(unused)]
fn main() {

    limiter.check_request(id).unwrap().allowed
}
}

Clock steps

The default MonotonicClock is immune to operating-system clock steps. It reads the OS clock once, when it is first used, and then measures elapsed time. A backwards step (an NTP correction, a manual change, a VM resuming with a stale clock) therefore has no effect on decisions, and capacity refills according to how much time really passed.

If you pass SystemClock explicitly you get wall-clock time instead, with its known limitation: a backwards step makes every client look over-limit until the OS clock catches back up, and no error is reported.

An earlier version of this page showed a workaround to layer on top of SystemClock: clamp its readings so they never go backwards. That is not a fix. The clamp freezes the limiter’s time at the instant of the step, so nothing refills until the OS clock climbs back past it. Measured, a client that waits 9.9 real seconds after a 10-second step gets none of the requests it has earned. Use MonotonicClock, which does not have the problem.

#![allow(unused)]
fn main() {
use axum::{
    body::Body,
    extract::State,
    http::{HeaderMap, Request, StatusCode},
    middleware::Next,
    response::{IntoResponse, Response},
};
use flux_limiter::{FluxLimiter, FluxLimiterError, MonotonicClock};
use std::sync::Arc;

type SharedLimiter = Arc<FluxLimiter<String, MonotonicClock>>;

// `from_fn` middleware always sees the concrete body type `Body`, so the
// request is `Request<Body>` and `Next` takes no generic parameter.
async fn rate_limit_middleware(
    State(limiter): State<SharedLimiter>,
    request: Request<Body>,
    next: Next,
) -> Result<Response, (StatusCode, HeaderMap, &'static str)> {
    // Extract client ID (e.g., from IP or auth header)
    let client_ip = extract_client_ip(&request);

    match limiter.check_request(client_ip) {
        Ok(decision) if decision.allowed => {
            // Add rate limit headers
            let mut response = next.run(request).await;
            if let Some(remaining) = decision.remaining_capacity {
                response.headers_mut().insert(
                    "X-RateLimit-Remaining",
                    remaining.to_string().parse().unwrap(),
                );
            }
            Ok(response)
        }
        Ok(decision) => {
            // Rate limited
            let mut headers = HeaderMap::new();
            if let Some(retry_after) = decision.retry_after_seconds {
                headers.insert(
                    "Retry-After",
                    (retry_after.ceil() as u64).to_string().parse().unwrap(),
                );
            }
            headers.insert("X-RateLimit-Remaining", "0".parse().unwrap());

            Err((StatusCode::TOO_MANY_REQUESTS, headers, "Rate limited"))
        }
        Err(FluxLimiterError::ClockError(_)) => {
            // Fail-open policy
            eprintln!("Rate limiter clock error - allowing request");
            Ok(next.run(request).await)
        }
        Err(e) => {
            eprintln!("Rate limiter error: {}", e);
            Err((StatusCode::INTERNAL_SERVER_ERROR, HeaderMap::new(), "Internal error"))
        }
    }
}

fn extract_client_ip<B>(request: &Request<B>) -> String {
    request
        .headers()
        .get("X-Forwarded-For")
        .and_then(|h| h.to_str().ok())
        .and_then(|s| s.split(',').next())
        .unwrap_or("unknown")
        .to_string()
}
}

    type Error = Error;
    type Transform = RateLimitMiddlewareService<S>;
    type InitError = ();
    type Future = Ready<Result<Self::Transform, Self::InitError>>;

    fn new_transform(&self, service: S) -> Self::Future {
        ready(Ok(RateLimitMiddlewareService {
            service,
            limiter: Arc::clone(&self.limiter),
        }))
    }
}

pub struct RateLimitMiddlewareService<S> {
    service: S,
    limiter: Arc<FluxLimiter<String, MonotonicClock>>,
}

impl<S> Service<ServiceRequest> for RateLimitMiddlewareService<S>
where
    S: Service<ServiceRequest, Response = ServiceResponse<BoxBody>, Error = Error>,
    S::Future: 'static,
{
    type Response = ServiceResponse<BoxBody>;
    type Error = Error;
    type Future = Pin<Box<dyn Future<Output = Result<Self::Response, Self::Error>>>>;

    fn poll_ready(
        &self,
        cx: &mut std::task::Context<'_>,
    ) -> std::task::Poll<Result<(), Self::Error>> {
        self.service.poll_ready(cx)
    }

    fn call(&self, req: ServiceRequest) -> Self::Future {
        let client_ip = req
            .connection_info()
            .realip_remote_addr()
            .unwrap_or("unknown")
            .to_string();

        let decision = self.limiter.check_request(client_ip);

        match decision {
            Ok(decision) if decision.allowed => {
                let fut = self.service.call(req);
                Box::pin(async move {
                    let mut res = fut.await?;
                    if let Some(remaining) = decision.remaining_capacity {
                        res.headers_mut().insert(
                            header::HeaderName::from_static("x-ratelimit-remaining"),
                            header::HeaderValue::from_str(&remaining.to_string()).unwrap(),
                        );
                    }
                    Ok(res)
                })
            }
            Ok(decision) => {
                let mut response = HttpResponse::TooManyRequests();
                if let Some(retry_after) = decision.retry_after_seconds {
                    response.insert_header((
                        "Retry-After",
                        (retry_after.ceil() as u64).to_string(),
                    ));
                }
                Box::pin(async move { Ok(req.into_response(response.finish())) })
            }
            Err(FluxLimiterError::ClockError(_)) => {
                // Fail-open policy
                eprintln!("Clock error - allowing request");
                let fut = self.service.call(req);
                Box::pin(async move { fut.await })
            }
            Err(e) => {
                eprintln!("Rate limiter error: {}", e);
                Box::pin(async move {
                    Ok(req.into_response(HttpResponse::InternalServerError().finish()))
                })
            }
        }
    }
}
}

Memory Monitoring

Monitor memory usage and alert on growth:

#![allow(unused)]
fn main() {
/// Rough estimate of the bytes held for `clients` clients whose keys are
/// `key_len` characters long.
///
/// The client map grows by doubling its tables, so memory holds flat for a
/// while and then jumps. This interpolates between measured averages over
/// large populations on a 64-bit target: about 76 bytes per client for a
/// 15-character `String` key and about 95 for a 36-character one. At any one
/// client count the true figure ranges from roughly 20% below to 15% above
/// the average, so size a capacity limit against the high end.
fn estimate_memory_usage(clients: usize, key_len: usize) -> usize {
    const MEASURED: [(usize, f64); 2] = [(15, 76.0), (36, 95.0)]; // (key length, bytes per client)
    let (lo, hi) = (MEASURED[0], MEASURED[1]);
    let per_client = if key_len <= lo.0 {
        lo.1
    } else if key_len >= hi.0 {
        // beyond the measured range, assume each extra character costs one byte
        hi.1 + (key_len - hi.0) as f64
    } else {
        lo.1 + (hi.1 - lo.1) * (key_len - lo.0) as f64 / (hi.0 - lo.0) as f64
    };
    (clients as f64 * per_client * 1.15).ceil() as usize // 1.15 = high end of the range
}

fn check_memory_threshold(limiter: &FluxLimiter<String, MonotonicClock>) {
    let client_count = limiter.client_count();
    let estimated_usage = estimate_memory_usage(client_count, "user_".len() + 36);
    let threshold = 100 * 1024 * 1024; // 100 MB

    if estimated_usage > threshold {
        warn!(
            "Rate limiter memory usage estimated at {} MB",
            estimated_usage / (1024 * 1024)
        );
    }
}
}

Error Handling Strategy

Circuit Breaker for Clock Errors

Temporarily disable rate limiting after persistent failures:

#![allow(unused)]
fn main() {
use std::sync::atomic::{AtomicU64, AtomicBool, Ordering};
use std::time::{SystemTime, Duration};

struct CircuitBreakerRateLimiter {
    limiter: FluxLimiter<String, MonotonicClock>,
    consecutive_failures: AtomicU64,
    circuit_open: AtomicBool,
    circuit_open_time: AtomicU64,
    failure_threshold: u64,
    reset_timeout_secs: u64,
}

impl CircuitBreakerRateLimiter {
    fn new(
        config: FluxLimiterConfig,
        failure_threshold: u64,
        reset_timeout_secs: u64,
    ) -> Result<Self, FluxLimiterError> {
        Ok(Self {
            limiter: FluxLimiter::with_config(config, MonotonicClock::new())?,
            consecutive_failures: AtomicU64::new(0),
            circuit_open: AtomicBool::new(false),
            circuit_open_time: AtomicU64::new(0),
            failure_threshold,
            reset_timeout_secs,
        })
    }

    fn check_request(&self, client_id: String) -> bool {
        // Check if circuit should be reset
        if self.circuit_open.load(Ordering::Relaxed) {
            let open_time = self.circuit_open_time.load(Ordering::Relaxed);
            let now = SystemTime::now()
                .duration_since(SystemTime::UNIX_EPOCH)
                .unwrap()
                .as_secs();

            if now - open_time > self.reset_timeout_secs {
                info!("Attempting to close circuit breaker");
                self.circuit_open.store(false, Ordering::Relaxed);
                self.consecutive_failures.store(0, Ordering::Relaxed);
            } else {
                // Circuit still open - bypass rate limiting
                return true;
            }
        }

        match self.limiter.check_request(client_id) {
            Ok(decision) => {
                // Reset failure counter on success
                self.consecutive_failures.store(0, Ordering::Relaxed);
                decision.allowed
            }
            Err(FluxLimiterError::ClockError(_)) => {
                let failures = self.consecutive_failures.fetch_add(1, Ordering::Relaxed) + 1;

                if failures >= self.failure_threshold {
                    error!(
                        "Opening circuit breaker after {} consecutive clock failures",
                        failures
                    );
                    self.circuit_open.store(true, Ordering::Relaxed);
                    let now = SystemTime::now()
                        .duration_since(SystemTime::UNIX_EPOCH)
                        .unwrap()
                        .as_secs();
                    self.circuit_open_time.store(now, Ordering::Relaxed);
                }

                true // Fail-open
            }
            Err(e) => {
                error!("Unexpected rate limiter error: {}", e);
                false
            }
        }
    }
}
}

Architecture Overview

This document provides a comprehensive overview of the Flux Limiter’s architecture, design decisions, and implementation details.

Design Philosophy

Flux Limiter is built on several key architectural principles:

  1. Fine-Grained Concurrency: Each client’s state is one atomic value, so updating a known client takes no lock
  2. Clock Abstraction: Enables testing, and lets the limiter use a monotonic clock by default
  3. Type Safety: Leverages Rust’s type system for correctness guarantees
  4. Errors Instead of Panics: Invalid configuration and a failed clock reading are returned as errors, so the application chooses how to respond

    ↓

    ↓

    ↓

    ↓

Key Design Principles

GCRA Algorithm

Deep dive into the Generic Cell Rate Algorithm implementation in Flux Limiter.

Algorithm Choice

Generic Cell Rate Algorithm (GCRA) was chosen over Token Bucket for several reasons:

  1. Mathematical Precision: Avoids floating-point precision issues
  2. Stateless Calculation: No background token refill processes
  3. Efficient State: One timestamp per client vs. token count + last refill
  4. Deterministic: Exact timing calculations with integer arithmetic

GCRA vs Token Bucket

Token Bucket

  • Maintains a count of available tokens
  • Tokens refill at a constant rate
  • Requests consume tokens
  • Requires background refill process or calculation on each check

GCRA

  • Maintains Theoretical Arrival Time (TAT)
  • Checks if current time conforms to rate
  • Updates TAT for next request
  • No background processes needed

Equivalence: GCRA and Token Bucket produce mathematically equivalent results, but GCRA is more efficient for implementation.

Core Concepts

Theoretical Arrival Time (TAT)

The TAT represents the theoretical time when the next request should arrive to maintain the configured rate.

Initial state:    TAT = 0
After request 1:  TAT = current_time + rate_interval
After request 2:  TAT = max(current_time, previous_TAT) + rate_interval

Rate Interval (T)

Time between consecutive requests at the configured rate:

T = 1 / rate_per_second
T_nanos = 1_000_000_000 / rate_per_second

Examples:

  • rate = 10.0 → T = 0.1s = 100_000_000 nanos
  • rate = 100.0 → T = 0.01s = 10_000_000 nanos
  • rate = 1000.0 → T = 0.001s = 1_000_000 nanos

Tolerance (τ)

Maximum allowed deviation from the rate, determined by burst capacity:

τ = burst_capacity * rate_interval
τ_nanos = burst_capacity * (1_000_000_000 / rate_per_second)

Examples with rate = 10.0:

  • burst = 0.0 → τ = 0 nanos (no burst)
  • burst = 5.0 → τ = 500_000_000 nanos (0.5 seconds)
  • burst = 10.0 → τ = 1_000_000_000 nanos (1 second)

Algorithm Implementation

Conformance Check

#![allow(unused)]
fn main() {
let current_time_nanos = clock.now()?;

if let Some(tat) = client_state.get(&client_id) {
    // Known client: no lock is held while deciding.
    let previous_tat_nanos = tat.load(Ordering::Relaxed);

    // Check if request conforms (is within tolerance)
    let is_conforming = current_time_nanos >=
        previous_tat_nanos.saturating_sub(tolerance_nanos);

    if is_conforming {
        let new_tat_nanos = current_time_nanos
            .max(previous_tat_nanos)
            .saturating_add(rate_nanos);
        // Publish only if the TAT is still the one we decided on;
        // otherwise another request got there first and we retry.
        tat.compare_exchange(previous_tat_nanos, new_tat_nanos, ...)?;
        // Return allowed decision
    } else {
        // Return denied decision with retry_after
    }
} else {
    // First request from this client. The entry lock is held only here.
    match client_state.entry(client_id) {
        Entry::Vacant(vacant) => {
            // Always allowed. Insert the initial TAT.
            vacant.insert(AtomicU64::new(
                current_time_nanos.saturating_add(rate_nanos),
            ));
            // Return allowed decision
        }
        Entry::Occupied(occupied) => {
            // Another request inserted this client first. Drop the guard so the
            // shard is not held, then retry the lock-free path on its value.
            drop(occupied);
            // ... retry as a known client, with a bounded number of attempts
        }
    }
}
}

A request that keeps losing the compare-and-swap retries up to 64 times. After that it takes the shard’s write lock once and settles the decision there, so a hot client cannot make a request spin forever. Even under that lock the store is a compare-and-swap, because the lock does not stop lock-free updates.

Conforming Request: current_time >= TAT - τ

This allows requests to arrive up to τ nanoseconds early (burst capacity).

The conformance check and TAT update are made atomic by the compare-and-swap: the new TAT is published only if it is still the value the check was computed from. A request that finds the TAT already advanced retries against the new value, so no update is lost and there is no TOCTOU race when the same client makes concurrent requests.

TAT Update (Allowed Request)

#![allow(unused)]
fn main() {
if is_conforming {
    // Compute the new TAT. The addition saturates rather than wrapping.
    let new_tat_nanos = current_time_nanos
        .max(previous_tat_nanos)
        .saturating_add(rate_nanos);

    // Publish it only if the TAT we decided on is still current. If another
    // request advanced it first, this fails and we retry on the new value.
    tat.compare_exchange(
        previous_tat_nanos,
        new_tat_nanos,
        Ordering::Relaxed,
        Ordering::Relaxed,
    )?;

    // Return allowed decision
}
}

No lock is held here. Relaxed ordering is sufficient because the atomic itself carries the ordering: a request either sees the TAT it decided on and wins the compare-and-swap, or sees a newer one and retries.

TAT Update Rule: TAT' = max(current_time, previous_TAT) + T

This ensures TAT advances by the rate interval while preventing it from going backward.

Mathematical Foundation

Basic Equations

  1. Rate Interval: T = 1 / r where r is rate per second
  2. Tolerance: τ = b * T where b is burst capacity
  3. TAT Update: TAT' = max(t, TAT) + T where t is current time
  4. Conformance: Request allowed if t >= TAT - τ

Burst Capacity

The burst capacity determines how many requests can be made immediately:

Total immediate capacity ≈ 1 + burst_capacity

Proof:

  • First request at t=0: TAT becomes T
  • Can make requests at times: 0, T-τ, 2T-τ, 3T-τ, ...
  • Maximum burst when all accumulated: τ/T = burst_capacity
  • Plus the current request: 1 + burst_capacity

Burst Recovery

After using burst capacity, it recovers at the configured rate:

Recovery rate = rate_per_second
Time to full recovery = burst_capacity / rate_per_second

Example with rate=10.0, burst=5.0:

  • Can burst 6 requests immediately
  • Recovers at 10 units/second
  • Full recovery in 0.5 seconds

Precision Guarantees

Nanosecond Arithmetic

All calculations use u64 nanoseconds:

#![allow(unused)]
fn main() {
// No floating-point drift
let rate_nanos: u64 = (1_000_000_000.0 / rate_per_second) as u64;
let tolerance_nanos: u64 = (burst_capacity * rate_nanos as f64) as u64;
}

Benefits:

  • Exact integer arithmetic
  • No accumulating rounding errors
  • Supports rates up to 1 billion requests/second
  • Nanosecond precision for timing

Overflow Protection

Uses saturating arithmetic to prevent overflow:

#![allow(unused)]
fn main() {
let is_conforming = current_time_nanos >=
    previous_tat_nanos.saturating_sub(tolerance_nanos);
}

Saturating operations:

  • saturating_sub: Returns 0 if underflow would occur
  • saturating_add: Returns u64::MAX if overflow would occur
  • Prevents undefined behavior and panics

pub fn validate(&self) -> Result<(), FluxLimiterError> {
    // `NaN` fails every comparison, so `is_finite` must reject it explicitly.
    if !self.rate_per_second.is_finite()
        || self.rate_per_second <= 0.0
        || self.rate_per_second > MAX_RATE_PER_SECOND
    {
        return Err(FluxLimiterError::InvalidRate);
    }
    if !self.burst_capacity.is_finite() || self.burst_capacity < 0.0 {
        return Err(FluxLimiterError::InvalidBurst);
    }
    Ok(())
}
}

Validation Rules:

  • Rate must be finite, positive (> 0.0), and at most 1,000,000,000 (the interval is whole nanoseconds)
  • Burst must be finite and non-negative (≥ 0.0)

  • Checked at construction time

A separate bound is enforced during construction rather than in validate(), because it depends on the derived interval: burst × (1e9 / rate) must fit in a u64, or construction fails with InvalidBurst. Known limitations:

  • A clock that steps backwards is not a source of ClockError: SystemTime::now() still succeeds, it simply returns an earlier value. Such a step makes clients look over-limit until the clock catches back up; this is why it is not the default; use MonotonicClock unless you need wall-clock time.

  • Suspend/resume and VM migration can produce a discontinuity, with the same consequence as above

Concurrency Model

Understanding the concurrency design in Flux Limiter.

Design in One Picture

Flux Limiter keeps one atomic value per client inside a sharded map. Updating a known client takes no lock at all; the map’s shard lock is taken only when a client is seen for the first time.

Multiple Threads
      ↓
FluxLimiter (Shared via Arc or Clone)
      ↓
Arc<DashMap<ClientId, AtomicU64>>     one TAT per client
      ↓
  known client   → load, decide, compare-and-swap   (no lock)
  new client     → insert under the shard lock      (once per client)

The word “lock-free” is used here in a precise sense. An update to a client that is already tracked takes no lock: it retries instead of waiting, so it makes progress as long as the thread running it gets to run. The map itself is built from sharded RwLocks, so finding a client and adding one the first time do take a brief lock on one shard.

There is one deliberate exception. A request that loses the compare-and-swap 64 times in a row stops retrying and settles under the shard’s write lock, where it waits for that lock. This only happens under extreme contention on a single client, and it is there so that a hot client cannot make a request retry forever.

Thread Safety Guarantees

1. Read Operations

Multiple concurrent readers without contention:

#![allow(unused)]
fn main() {
// Thread 1
limiter.check_request("client_1")?;

// Thread 2 (concurrent)
limiter.check_request("client_2")?;

// Both take the fast path: no lock is held while deciding
}

2. Write Operations

A compare-and-swap on the client’s atomic TAT. The new TAT is published only if the TAT is still the one the decision was computed from:

#![allow(unused)]
fn main() {
let previous_tat = tat.load(Ordering::Relaxed);
let decision = decide(previous_tat, now);          // pure: reads no shared state
if decision.allowed {
    tat.compare_exchange(
        previous_tat,                               // only if unchanged
        decision.reset_time_nanos,
        Ordering::Relaxed,
        Ordering::Relaxed,
    )?;                                             // otherwise: retry
}
}

A request that loses the race (another request advanced the TAT first) retries from the new value, so each allowed request advances the TAT by exactly one interval. No update can be lost, which is what prevents the TOCTOU race conditions that a plain read-then-write would allow when the same client makes concurrent requests.

A client’s first request is different: it has no TAT to compare against, so it is inserted under the shard’s write lock through DashMap’s entry() API. If two requests race to insert the same new client, the loser finds the entry occupied and rejoins the compare-and-swap path rather than being granted a second “first” request.

3. Memory Ordering

Relaxed ordering is sufficient for TAT updates:

  • TAT values are monotonically increasing
  • No cross-client dependencies
  • No ABA problem

4. Concurrent Access Patterns

Same Client, Different Threads:

#![allow(unused)]
fn main() {
// Thread 1
limiter.check_request("client_1")?; // TAT = 100ms

// Thread 2 (concurrent)
limiter.check_request("client_1")?; // TAT = 200ms

// Each request publishes its TAT with a compare-and-swap.
// The one that loses retries on the winner's value, so
// the TAT ends at 300ms, never back at 200ms.
}

Different Clients, Different Threads:

#![allow(unused)]
fn main() {
// Thread 1
limiter.check_request("client_1")?;

// Thread 2 (concurrent)
limiter.check_request("client_2")?;

// Two different atomics: the updates are independent.
// They only queue if both clients hash to the same shard
// *and* one of them is being inserted for the first time.
}

DashMap: The Core Concurrency Primitive

Why DashMap?

DashMap provides concurrent access through sharding. Each shard is a plain HashMap behind an RwLock, so a lookup takes a shared read lock on one shard and an insert takes that shard’s write lock:

DashMap<ClientId, AtomicU64>
    ├─ Shard 0: HashMap + RwLock
    ├─ Shard 1: HashMap + RwLock
    ├─ Shard 2: HashMap + RwLock
    ├─ ...
    └─ Shard N: HashMap + RwLock

Why the per-client atomic sits on top of it:

  • The shard lock is only needed to find or add a client, which is a small fraction of the work
  • The GCRA decision and the TAT update, which happen on every request, never hold a lock
  • Without the atomic, every request would need the shard’s write lock, so every client in a shard would serialize behind every other
  • Better than std::HashMap + Mutex: One stuck shard does not stall the rest
  • Better than custom lock-free map: Mature, battle-tested

Sharding Strategy

Operations on DashMap

Update a known client (compare-and-swap, no lock):

#![allow(unused)]
fn main() {
if let Some(tat) = client_state.get(&client_id) {
    // `tat` is a Ref<Entry to AtomicU64>: a shared read lock on the shard.
    let previous = tat.load(Ordering::Relaxed);
    let decision = decide(previous, now);
    if decision.allowed {
        tat.compare_exchange(previous, decision.reset_time_nanos, ...)?;
    }
}
}

Insert a new client (shard write lock, once per client):

#![allow(unused)]
fn main() {
match client_state.entry(client_id) {
    Entry::Vacant(entry) => entry.insert(AtomicU64::new(now + interval)),
    Entry::Occupied(_) => { /* lost the race: use the update path above */ }
}
}

Together these keep the conformance check and TAT update atomic per client, preserving the GCRA invariant even under concurrent access.

Cleanup (Iteration):

#![allow(unused)]
fn main() {
client_state.retain(|_, tat| {
    // Locks each shard sequentially
    // Short lock duration per shard
    tat.load(Ordering::Relaxed) + tolerance > cutoff
});
}

Memory Consistency

Happens-Before Relationships

DashMap provides happens-before guarantees:

#![allow(unused)]
fn main() {
// Thread 1
limiter.check_request("client_1")?; // Writes TAT = 100ms

// Thread 2 (later)
limiter.check_request("client_1")?; // Reads TAT >= 100ms
}

The write in Thread 1 happens-before the read in Thread 2.

Visibility Guarantees

All updates to client state are immediately visible:

#![allow(unused)]
fn main() {
// Thread 1: compare-and-swap publishes the new TAT
tat.compare_exchange(99, 100, Ordering::Relaxed, Ordering::Relaxed)?;

// Thread 2, afterwards
if let Some(tat) = client_state.get("client_1") {
    tat.load(Ordering::Relaxed); // 100
}
}

Relaxed is enough here because the TAT is a single self-contained value with no other memory it needs to publish. “Afterwards” is guaranteed by the compare-and-swap itself: a request that reads 99 and tries to write 100 fails if anyone else already moved the TAT on.

Contention Analysis

Low Contention Scenarios

Different clients, concurrent access:

Threads: [T1: client_1] [T2: client_2] [T3: client_3]
Shards:  [Shard 0    ] [Shard 1    ] [Shard 2    ]
Result:  Independent atomics, shared read locks only

Medium Contention Scenarios

Same shard, different clients:

Threads: [T1: client_1] [T2: client_100]
Shards:  [Shard 0    ] [Shard 0      ]
Result:  Shared read lock only; still independent atomics

High Contention Scenarios

Same client, concurrent access:

Threads: [T1: client_1] [T2: client_1] [T3: client_1]
Shards:  [Shard 0    ] [Shard 0    ] [Shard 0    ]
TAT:     one atomic, three compare-and-swaps
Result:  No lock; requests that collide retry on the winner's value

Correctness does not depend on serialization. The invariant is that each allowed request advances the TAT by one interval. A compare-and-swap enforces that without a queue: whichever request wins moves the TAT, and the others recompute against the new value.

Performance Under Concurrency

Scalability Characteristics

Different clients  → different atomics   (independent, scales well)
Same client        → one atomic         (compare-and-swap, no lock)

Requests for different clients never wait on each other’s TAT. Requests for the same client do not queue: each one that loses a compare-and-swap retries, and the retry count rises with contention rather than the wait time.

Benchmarking concurrent access

The repository has Criterion benchmarks for exactly these two cases. They produced the figures in Performance Design, and they are the right way to check a change against them:

cargo bench contention
BenchmarkWhat it measures
contention_hot_key_u644 threads, all hitting one client: the worst case for same-client contention
contention_spread_keys_u644 threads, each with its own clients: the common case

Both are reported per request, with throughput in requests per second.

If you write your own, three things decide whether the number means anything:

  • Start the threads before the timed region. Starting a thread costs tens of microseconds, which is hundreds of times the cost of a request. The repository’s benchmarks start their workers once and release them on a channel for each timed round.
  • Make sure requests are allowed. A denied request never touches the client’s state, so a run that is mostly denials measures nothing about contention. Use a high rate so that every request writes.
  • Release the threads together. Same-client requests only collide when they arrive at the same moment. Threads that start in a stagger take turns instead of contending, and the result looks far better than the worst case.

Rust’s built-in #[bench] attribute is not stable and needs a nightly toolchain, which is why the crate uses Criterion.

Best Practices

1. Share via Arc or Clone

#![allow(unused)]
fn main() {
// Option A: Share limiter across threads via Arc
let limiter = Arc::new(FluxLimiter::with_config(config, clock)?);

// Option B: Clone the limiter directly (shares the same DashMap)
let limiter = FluxLimiter::with_config(config, clock)?;
let limiter2 = limiter.clone();

// Bad: Create multiple limiters (separate state)
let limiter1 = FluxLimiter::with_config(config, clock1)?;
let limiter2 = FluxLimiter::with_config(config, clock2)?;
}

2. Know What a Hot Client Costs

#![allow(unused)]
fn main() {
// Independent clients: one atomic each, no interaction
for i in 0..1000 {
    limiter.check_request(format!("client_{}", i))?;
}

// One client from many threads: every request is a compare-and-swap on
// the same atomic. Correct, and lock-free, but the retries are real work:
limiter.check_request("same_client")?;
}

A single very hot client does not block anyone, but it is the one pattern where contention is visible. It is also the pattern rate limiting exists for, so it is never something to avoid on the limiter’s account.

3. Avoid Blocking in Callbacks

#![allow(unused)]
fn main() {
// Good: Quick check
match limiter.check_request(client_id) {
    Ok(decision) => decision.allowed,
    Err(_) => false,
}

// Bad: Blocking I/O while holding client state
match limiter.check_request(client_id) {
    Ok(decision) => {
        // Don't do expensive work here
        database.log_decision(decision)?; // Blocks!
        decision.allowed
    }
    Err(_) => false,
}
}

4. Periodic Cleanup

#![allow(unused)]
fn main() {
// Background cleanup task
tokio::spawn(async move {
    let mut interval = interval(Duration::from_secs(3600));
    loop {
        interval.tick().await;
        let _ = limiter.cleanup_stale_clients(threshold);
    }
});
}

Error Handling Architecture

Comprehensive error handling design for production reliability.

Error Type Hierarchy

FluxLimiterError
├── InvalidRate        (Configuration)
├── InvalidBurst       (Configuration)
└── ClockError         (Runtime)
    └── SystemTimeError

Design Principles

1. Explicit Error Types

No silent failures - all errors are explicitly typed:

#![allow(unused)]
fn main() {
pub enum FluxLimiterError {
    InvalidRate,            // Rate non-finite, ≤ 0, or > 1e9
    InvalidBurst,           // Burst non-finite, < 0, or too large to fit
    ClockError(ClockError), // A clock reading failed
}
}

2. Configuration vs Runtime Errors

Configuration Errors (at startup):

  • InvalidRate: Caught during limiter creation
  • InvalidBurst: Caught during limiter creation
  • Should never occur in production after startup

Runtime Errors (during operation):

  • ClockError: only if you use SystemClock or a custom clock
  • The default MonotonicClock never produces it
  • Requires graceful handling
  • Application chooses policy

3. Graceful Degradation

Applications can choose error handling policy:

  • Fail-open: Allow requests on errors
  • Fail-closed: Deny requests on errors
  • Fallback: Use alternative rate limiting

Configuration Error Handling

Early Validation

Validate configuration at startup:

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = FluxLimiterConfig::new(100.0, 50.0);

    let limiter = FluxLimiter::with_config(config, MonotonicClock::new())
        .map_err(|e| match e {
            FluxLimiterError::InvalidRate => {
                "Invalid rate: must be positive".to_string()
            }
            FluxLimiterError::InvalidBurst => {
                "Invalid burst: must be non-negative".to_string()
            }
            _ => format!("Configuration error: {}", e),
        })?;

    // Use limiter...
    Ok(())
}

Explicit Validation

#![allow(unused)]
fn main() {
impl FluxLimiterConfig {
    pub fn validate(&self) -> Result<(), FluxLimiterError> {
        if !self.rate_per_second.is_finite()
            || self.rate_per_second <= 0.0
            || self.rate_per_second > MAX_RATE_PER_SECOND
        {
            return Err(FluxLimiterError::InvalidRate);
        }
        if !self.burst_capacity.is_finite() || self.burst_capacity < 0.0 {
            return Err(FluxLimiterError::InvalidBurst);
        }
        Ok(())
    }
}
}

When to use:

  • Before storing configuration
  • When loading from external sources
  • Before creating rate limiter

Runtime Clock Errors

Clock Error Sources

The default MonotonicClock never returns a ClockError. The error has one source, and only if you opt into SystemClock or write your own clock:

  1. System Time Unavailable
    • SystemClock could not read the system clock, which happens only if the clock is before the Unix epoch
    • Reported as ClockError::SystemTimeError

With the default clock, the Err arm of check_request can only be reached through a bug in a custom clock. Handling it is still correct, because the return type allows it, but it is not a path you should expect to run.

What is not a clock error

A clock that steps backwards is not a source of ClockError. Reading the clock still succeeds and simply returns an earlier value. With SystemClock that makes every client look over-limit until the clock catches back up, and no error is reported. This is why SystemClock is not the default: the MonotonicClock measures elapsed time and is unaffected by a step.

Error Propagation

Clock::now() → Result<u64, ClockError>
     ↓
FluxLimiter::check_request() → Result<Decision, FluxLimiterError>
     ↓
Application Layer → Implements error policy

Handling Clock Errors

Fail-Open Policy

Allow requests when clock fails:

#![allow(unused)]
fn main() {
match limiter.check_request(client_id) {
    Ok(decision) => decision.allowed,
    Err(FluxLimiterError::ClockError(_)) => {
        eprintln!("Clock error - allowing request (fail-open)");
        true
    }
    Err(e) => {
        eprintln!("Unexpected error: {}", e);
        true
    }
}
}

Use when:

  • Availability > strict rate limiting
  • False positives acceptable
  • Backend can handle spikes

Fail-Closed Policy

Deny requests when clock fails:

#![allow(unused)]
fn main() {
match limiter.check_request(client_id) {
    Ok(decision) => decision.allowed,
    Err(FluxLimiterError::ClockError(_)) => {
        eprintln!("Clock error - denying request (fail-closed)");
        false
    }
    Err(e) => {
        eprintln!("Unexpected error: {}", e);
        false
    }
}
}

Use when:

  • Security paramount
  • False negatives acceptable
  • Protecting backend critical

Fallback Policy

Use alternative when clock fails:

#![allow(unused)]
fn main() {
use std::sync::atomic::{AtomicU64, Ordering};

static FALLBACK_COUNTER: AtomicU64 = AtomicU64::new(0);
const FALLBACK_LIMIT: u64 = 1000;

match limiter.check_request(client_id) {
    Ok(decision) => decision.allowed,
    Err(FluxLimiterError::ClockError(_)) => {
        let count = FALLBACK_COUNTER.fetch_add(1, Ordering::Relaxed);
        count < FALLBACK_LIMIT
    }
    Err(_) => false,
}
}

Use when:

  • Need graceful degradation
  • Have fallback mechanism
  • Want best effort

Error Monitoring

Tracking Error Rates

#![allow(unused)]
fn main() {
use std::sync::atomic::{AtomicU64, Ordering};

struct ErrorMetrics {
    total_requests: AtomicU64,
    clock_errors: AtomicU64,
    config_errors: AtomicU64,
}

impl ErrorMetrics {
    fn record_result(&self, result: &Result<FluxLimiterDecision, FluxLimiterError>) {
        self.total_requests.fetch_add(1, Ordering::Relaxed);

        if let Err(e) = result {
            match e {
                FluxLimiterError::ClockError(_) => {
                    self.clock_errors.fetch_add(1, Ordering::Relaxed);
                }
                FluxLimiterError::InvalidRate | FluxLimiterError::InvalidBurst => {
                    self.config_errors.fetch_add(1, Ordering::Relaxed);
                }
            }
        }
    }

    fn error_rate(&self) -> f64 {
        let total = self.total_requests.load(Ordering::Relaxed);
        let errors = self.clock_errors.load(Ordering::Relaxed);

        if total == 0 {
            0.0
        } else {
            errors as f64 / total as f64
        }
    }
}
}

Alerting on Errors

#![allow(unused)]
fn main() {
fn check_with_alerting(
    limiter: &FluxLimiter<String, MonotonicClock>,
    metrics: &ErrorMetrics,
    client_id: String,
) -> bool {
    let result = limiter.check_request(client_id);
    metrics.record_result(&result);

    // Alert if error rate exceeds threshold
    if metrics.error_rate() > 0.01 {
        eprintln!(
            "ALERT: Clock error rate exceeded 1%: {:.2}%",
            metrics.error_rate() * 100.0
        );
    }

    match result {
        Ok(decision) => decision.allowed,
        Err(FluxLimiterError::ClockError(_)) => true, // Fail-open
        Err(_) => false,
    }
}
}

Circuit Breaker Pattern

Temporarily bypass rate limiting after consecutive failures:

#![allow(unused)]
fn main() {
use std::sync::atomic::{AtomicU64, AtomicBool, Ordering};

struct CircuitBreaker {
    consecutive_failures: AtomicU64,
    circuit_open: AtomicBool,
    threshold: u64,
}

impl CircuitBreaker {
    fn new(threshold: u64) -> Self {
        Self {
            consecutive_failures: AtomicU64::new(0),
            circuit_open: AtomicBool::new(false),
            threshold,
        }
    }

    fn record_success(&self) {
        self.consecutive_failures.store(0, Ordering::Relaxed);
        self.circuit_open.store(false, Ordering::Relaxed);
    }

    fn record_failure(&self) -> bool {
        let failures = self.consecutive_failures.fetch_add(1, Ordering::Relaxed) + 1;

        if failures >= self.threshold {
            if !self.circuit_open.swap(true, Ordering::Relaxed) {
                eprintln!("Circuit breaker opened after {} failures", failures);
            }
            true
        } else {
            false
        }
    }

    fn is_open(&self) -> bool {
        self.circuit_open.load(Ordering::Relaxed)
    }
}

fn check_with_circuit_breaker(
    limiter: &FluxLimiter<String, MonotonicClock>,
    breaker: &CircuitBreaker,
    client_id: String,
) -> bool {
    if breaker.is_open() {
        return true; // Bypass rate limiting
    }

    match limiter.check_request(client_id) {
        Ok(decision) => {
            breaker.record_success();
            decision.allowed
        }
        Err(FluxLimiterError::ClockError(_)) => {
            breaker.record_failure();
            true // Fail-open
        }
        Err(_) => false,
    }
}
}

Error Recovery Strategies

1. Retry with Backoff

#![allow(unused)]
fn main() {
async fn check_with_retry(
    limiter: &FluxLimiter<String, MonotonicClock>,
    client_id: String,
    max_retries: u32,
) -> Result<FluxLimiterDecision, FluxLimiterError> {
    let mut retries = 0;
    let mut delay = Duration::from_millis(10);

    loop {
        match limiter.check_request(client_id.clone()) {
            Ok(decision) => return Ok(decision),
            Err(FluxLimiterError::ClockError(_)) if retries < max_retries => {
                eprintln!("Clock error, retrying in {:?}", delay);
                tokio::time::sleep(delay).await;
                delay *= 2;
                retries += 1;
            }
            Err(e) => return Err(e),
        }
    }
}
}

2. Degrade Gracefully

#![allow(unused)]
fn main() {
enum RateLimitStrategy {
    Primary(FluxLimiter<String, MonotonicClock>),
    Fallback(SimpleCounter),
}

impl RateLimitStrategy {
    fn check_request(&mut self, client_id: String) -> bool {
        match self {
            Self::Primary(limiter) => {
                match limiter.check_request(client_id) {
                    Ok(decision) => decision.allowed,
                    Err(FluxLimiterError::ClockError(_)) => {
                        // Switch to fallback
                        eprintln!("Switching to fallback strategy");
                        *self = Self::Fallback(SimpleCounter::new());
                        true
                    }
                    Err(_) => false,
                }
            }
            Self::Fallback(counter) => counter.check(),
        }
    }
}
}

Performance Design

Deep dive into performance optimization techniques and characteristics.

Hot Path Optimization

The check_request() method is optimized for minimal latency:

Execution Path

#![allow(unused)]
fn main() {
pub fn check_request(&self, client_id: T) -> Result<FluxLimiterDecision, FluxLimiterError> {
    // 1. Single clock call
    let current_time_nanos = self.clock.now()?;

    // 2. Look up the client (shared read lock on one shard)
    if let Some(tat) = self.client_state.get(&client_id) {
        let previous_tat_nanos = tat.load(Ordering::Relaxed);

        // 3. Integer arithmetic
        let is_conforming = current_time_nanos >=
            previous_tat_nanos.saturating_sub(self.tolerance_nanos);

        // 4. Publish the new TAT, only if unchanged (no lock)
        if is_conforming {
            let new_tat_nanos = current_time_nanos
                .max(previous_tat_nanos)
                .saturating_add(self.rate_nanos);
            tat.compare_exchange(previous_tat_nanos, new_tat_nanos, ...)?;
        }
        // ... return decision
    } else {
        // First request from this client — always allowed (shard write lock)
        // ... insert initial TAT, return allowed decision
    }

    // 5. Metadata calculation
    // 6. Return decision
}
}

The hot path involves a single clock call, a single map lookup, one atomic compare-and-swap, and simple integer arithmetic — all O(1).

Optimization Techniques

  1. Single Clock Call: One time source access per request
  2. No Lock on the Update: a compare-and-swap publishes the new TAT, so requests for the same client do not queue behind a shard’s write lock
  3. Integer Arithmetic: No floating-point operations in hot path
  4. Minimal Branching: Straight-line execution

Concurrency Performance

Where the Locks Are

DashMap is sharded: each shard is a HashMap behind an RwLock. On top of it, each client’s TAT is an AtomicU64. The two together decide what locks:

Different clients → different shards (low contention)
Same client     → one atomic  (compare-and-swap, no lock)
Short critical sections → minimal lock duration

What takes a lock, and what does not:

  • Updating a known client: no lock (compare-and-swap on its atomic)
  • Looking up a client: that shard’s read lock, shared with other lookups
  • Inserting a client for the first time: that shard’s write lock, once per client
  • cleanup_stale_clients: each shard’s write lock in turn

Measured with 4 threads on one client (i7-13700HX, criterion, 1,000 requests per iteration): 159 ns per request before the atomic TAT, and 67 to 96 ns per request after it, over nine runs. That makes it roughly 1.6 to 2.4 times faster. The figure moves by about 40% between runs, which happens when threads contend for one key on a laptop, so treat the range as the result and not any single number in it. Four threads on distinct clients take 31 ns per request and stay within 3% between runs, since they were never waiting on the same lock to begin with.

Optimization Decisions

Integer Arithmetic vs Floating-Point

Integer (chosen):

  • ✅ Exact precision
  • ✅ Faster arithmetic
  • ✅ No rounding errors
  • ✅ Cache-friendly (u64)

Floating-point (rejected):

  • ❌ Precision loss
  • ❌ Slower arithmetic
  • ❌ Accumulating errors
  • ❌ Larger memory footprint

DashMap vs Alternatives

DashMap (chosen):

  • ✅ Sharded locks, so one busy shard does not stall the others
  • ✅ With an atomic per client, the per-request update needs no lock at all
  • ✅ Battle-tested
  • ✅ Ergonomic API

Mutex<HashMap> (rejected):

  • ❌ Global locking
  • ❌ Poor scalability
  • ❌ Read contention

RwLock<HashMap> (rejected):

  • ❌ Reader/writer contention
  • ❌ Write starvation possible

Custom lock-free map (rejected):

  • ❌ Implementation complexity
  • ❌ Maintenance burden
  • ❌ Potential bugs

Nanosecond Precision

u64 nanoseconds (chosen):

  • ✅ Maximum precision
  • ✅ Integer arithmetic
  • ✅ No overflow for 584 years
  • ✅ Direct system time conversion

Milliseconds (rejected):

  • ❌ Insufficient for high rates
  • ❌ Precision loss

Duration (rejected):

  • ❌ Larger memory footprint
  • ❌ More complex arithmetic

TestClock Design

The TestClock is the foundation for deterministic testing.

Implementation

#![allow(unused)]
fn main() {
use std::sync::Arc;
use std::sync::atomic::{AtomicU64, AtomicBool, Ordering};

pub struct TestClock {
    time: Arc<AtomicU64>,        // Current time in nanoseconds
    should_fail: Arc<AtomicBool>, // Failure simulation flag
}

impl TestClock {
    pub fn new(initial_time_secs: f64) -> Self {
        Self {
            time: Arc::new(AtomicU64::new((initial_time_secs * 1e9) as u64)),
            should_fail: Arc::new(AtomicBool::new(false)),
        }
    }

    pub fn advance(&self, duration_secs: f64) {
        let duration_nanos = (duration_secs * 1e9) as u64;
        self.time.fetch_add(duration_nanos, Ordering::SeqCst);
    }

    pub fn set_time(&self, time_secs: f64) {
        self.time.store((time_secs * 1e9) as u64, Ordering::SeqCst);
    }

    pub fn fail_next_call(&self) {
        self.should_fail.store(true, Ordering::SeqCst);
    }
}

impl Clock for TestClock {
    fn now(&self) -> Result<u64, ClockError> {
        if self.should_fail.swap(false, Ordering::SeqCst) {
            return Err(ClockError::SystemTimeError);
        }
        Ok(self.time.load(Ordering::SeqCst))
    }
}
}

Key Features

  1. Deterministic Time: Controlled time progression
  2. Thread-Safe: Can be shared across test threads
  3. Failure Simulation: Can simulate clock errors
  4. Precise Control: Nanosecond-level manipulation

Design Decisions

Detailed rationale behind key architectural choices in Flux Limiter.

Algorithm Selection: GCRA vs Token Bucket

Decision: Use GCRA

Rationale: The Generic Cell Rate Algorithm (GCRA) provides mathematical equivalence to Token Bucket with several implementation advantages.

GCRA Advantages

✅ Exact Mathematical Precision

  • Integer arithmetic with u64 nanoseconds
  • No floating-point state, so nothing drifts as requests accumulate
  • The rate is truncated once, to a whole-nanosecond interval; see below

✅ Stateless Calculation

  • No background token refill processes
  • No timer management overhead
  • Simpler implementation

✅ Efficient State

  • One timestamp (u64) per client
  • vs. token count + last refill time
  • Smaller memory footprint

✅ Deterministic Behavior

  • Exact timing with integer arithmetic
  • Predictable results in tests
  • No timer drift

Token Bucket Drawbacks

❌ Floating-Point Precision

  • Token counts as floats
  • Accumulating rounding errors
  • Precision loss over time

❌ Background Processes

  • Requires token refill mechanism
  • Timer management complexity
  • Potential drift issues

❌ Complex State

  • Token count + timestamp
  • More memory per client
  • More complex updates

Mathematical Equivalence

Both algorithms produce the same rate limiting behavior:

GCRA: Request allowed if current_time >= TAT - tolerance
Token Bucket: Request allowed if tokens >= 1

The difference is implementation, not behavior.

Data Structure: DashMap

Decision: Use DashMap for Client State

Rationale: DashMap provides the best balance of performance, correctness, and ergonomics.

DashMap Benefits

✅ Fine-Grained Concurrency

  • Each client’s TAT is an AtomicU64, updated by compare-and-swap with no lock
  • Only lookups and first-time inserts take a (sharded) lock
  • Requests for different clients never wait on each other

✅ Battle-Tested

  • Mature library
  • Well-documented
  • Proven in production

✅ Good Performance

  • Efficient operations
  • Minimal overhead
  • Efficient memory layout

✅ Ergonomic API

  • Similar to std::HashMap
  • Easy to use correctly
  • Clear semantics

Alternative: Mutex<HashMap>

❌ Global Locking

  • All operations serialize
  • Poor scalability
  • Read contention

Why rejected: Unacceptable performance bottleneck for concurrent access.

Alternative: RwLock<HashMap>

❌ Reader/Writer Contention

  • Writers block all readers
  • Write starvation possible
  • Complex lock management

Why rejected: Still has contention issues, doesn’t scale well.

Alternative: Custom Lock-Free Map

❌ Implementation Complexity

  • Requires deep concurrency expertise
  • Bug-prone
  • High maintenance burden

❌ Maturity Risk

  • Unproven in production
  • Potential correctness issues
  • Performance unknowns

Why rejected: Not worth the complexity and risk when DashMap exists.

Time Representation: Nanoseconds

Decision: Use u64 Nanoseconds

Rationale: Nanoseconds give fine resolution with integer arithmetic, so every timing decision is reproducible.

Benefits

✅ Fine Resolution

  • One nanosecond per unit
  • Rates up to 1 billion per second can be represented
  • The precision limit is the rate, not the timestamp: see below

✅ Integer Arithmetic

  • No floating-point state
  • Deterministic results
  • Once the rate is an interval, the arithmetic has no rounding error

✅ No Overflow

  • u64::MAX nanoseconds is about 584 years
  • All additions saturate rather than wrap, so an out-of-range value cannot evict a live client or panic
  • The rate and burst are validated before any timestamp is computed from them

✅ System Time Compatible

  • Direct conversion from SystemTime
  • No conversion overhead
  • Natural representation

⚠️ Known limitation: the rate is truncated to a whole number of nanoseconds

  • rate is stored as the interval 1_000_000_000 / rate, truncated
  • A rate that does not divide one billion is enforced slightly higher than requested
  • Below about 10 million per second the difference is under 1%; at rate = 6e8 it is 67%
  • See Configuration: precision

Alternative: Milliseconds

❌ Insufficient Resolution

  • One millisecond per unit, so no rate above 1000 per second can be represented
  • The same truncation that affects high rates in nanoseconds would affect every rate above 1000
  • Burst tolerance would be coarser by a factor of a million

Why rejected: Caps the supported rate far below what users ask for.

Alternative: Duration Type

❌ Memory Overhead

  • Larger struct (2x u64)
  • More complex arithmetic
  • Cache inefficient

❌ Performance

  • More expensive operations
  • Additional abstractions
  • Not necessary

Why rejected: Overhead without benefit for our use case.

Alternative: f64 Seconds

❌ Floating-Point Issues

  • Precision loss
  • Rounding errors
  • Non-deterministic

❌ Performance

  • Slower arithmetic
  • Cache less friendly
  • Conversion overhead

Why rejected: Precision and performance concerns.

Error Handling: Result Types

Decision: Use Result for All Errors

Rationale: Explicit error handling enables graceful degradation and better observability.

Benefits

✅ Explicit Error Handling

  • Caller must handle errors
  • No silent failures
  • Clear error paths

✅ Graceful Degradation

  • Application chooses policy
  • Fail-open or fail-closed
  • Fallback strategies possible

✅ Better Observability

  • Errors can be logged
  • Metrics can be collected
  • Debugging easier

✅ Production-Ready

  • Handles clock failures
  • Recoverable errors
  • Robust operation

Alternative: Panics

❌ Difficult Recovery

  • Can’t recover from panic
  • Crashes entire application
  • Poor user experience

❌ Poor Observability

  • Hard to monitor
  • Difficult to debug
  • No graceful degradation

❌ Not Production-Ready

  • Unacceptable for library code
  • Forces policy on users
  • Fragile

Why rejected: Panics are inappropriate for library code and prevent graceful error handling.

Alternative: Silent Failures (allow on error)

❌ Hidden Bugs

  • Errors go unnoticed
  • Hard to debug
  • Incorrect behavior

❌ No Observability

  • Can’t track error rates
  • No alerting possible
  • Silent degradation

Why rejected: Silent failures make debugging impossible and hide problems.

Decision: Generic Client ID (T: Hash + Eq + Clone)

Rationale: Generics provide flexibility while maintaining type safety and performance.

Benefits

✅ Flexibility

  • String: User IDs, API keys
  • IpAddr: IP-based limiting
  • u64: Numeric IDs
  • Custom types: Complex scenarios

✅ Zero-Cost Abstraction

  • No boxing/dynamic dispatch
  • Compile-time optimization

✅ Type Safety

  • Can’t mix different ID types
  • Clear API

✅ Performance

  • Inlined operations
  • Optimal code generation

  • Slower performance

❌ Less Ergonomic

  • More verbose usage

  • Always allocates
  • Slower hash/compare
  • Memory overhead

Why rejected: Generics provide flexibility without cost.

Clock Abstraction

Decision: Clock Trait

Rationale: Abstracting time enables testing, and lets the limiter use a monotonic source instead of the operating system’s wall clock.

Benefits

✅ Testable

  • TestClock for deterministic tests
  • Precise time control
  • Failure simulation

✅ Independent of the OS clock

  • The default MonotonicClock measures elapsed time, so a backwards clock step does not affect decisions
  • It reads the OS clock once, to anchor its readings to the Unix epoch
  • It never returns an error

⚠️ Known limitation: wall-clock time, if you opt into it

  • SystemClock reads the OS clock directly
  • That clock can step backwards (NTP, manual change, VM migration)
  • SystemClock does not detect this and does not return an error
  • Clients then appear over-limit until the clock catches up
  • This is why it is not the default

✅ Flexible

  • Custom time sources
  • Mock implementations
  • Production/test separation

✅ Error Handling

  • Graceful clock failures
  • Explicit error types
  • Recoverable

Alternative: Direct SystemTime

❌ Not Testable

  • Can’t control time in tests
  • Non-deterministic tests
  • Hard to test edge cases

❌ No Error Handling

  • SystemTime can fail
  • Can’t recover
  • Silent failures

Why rejected: Testing and error handling require abstraction.

Memory Management: Manual Cleanup

Decision: Explicit cleanup_stale_clients()

Rationale: Manual cleanup gives users control over memory/CPU tradeoff.

Benefits

✅ User Control

  • Choose cleanup frequency
  • Choose threshold
  • Tune for workload

✅ No Background Threads

  • Simpler implementation
  • No thread overhead
  • User controls when

✅ Predictable Performance

  • Cleanup only when called
  • No surprising pauses
  • Controllable overhead

Alternative: Automatic Background Cleanup

❌ Thread Overhead

  • Requires background thread
  • Thread management complexity
  • Resource usage

❌ Loss of Control

  • Can’t control timing
  • Fixed thresholds
  • May not fit all workloads

❌ Complexity

  • Thread lifecycle management
  • Shutdown coordination
  • Error handling

Why rejected: Manual cleanup is simpler and more flexible.

Alternative: Reference Counting

❌ Incorrect Semantics

  • Clients don’t have clear ownership
  • Memory leak if client keeps requesting
  • Doesn’t solve problem

Why rejected: Doesn’t match use case.

Benefits

✅ Flexible

✅ Validation

  • Fail fast

Default Type Parameter

The existing API surface is kept by a default on the clock parameter rather than by type aliases (two aliases cannot share one name):

#![allow(unused)]
fn main() {
// `FluxLimiter<T>` is already the common spelling, because `C` defaults:

// Users who need another clock name it explicitly:

}

Any future change must keep both spellings working: FluxLimiter<T> and FluxLimiter<T, C>.
